# Native HTTP MPEG-TS broadcast sources (#206)

Status: approved by the user on 2026-10-23, including the documented per-platform durability boundary and RTMP broadcast-operation cleanup boundary below. Implementation planning is authorized; root must present the saved implementation plan for human confirmation before behavior edits.

## Intent and boundaries

Let an operator attach an HTTP(S) MPEG-TS origin to a named broadcast without an external pipe. One engine-owned worker fetches, signs, stores and reconnects through the existing broadcast path. The broadcast's signing identity and monotonically allocated piece indexes survive reconnects and daemon restarts.

The user selected: environment-configured sources reattach at startup; API attachments last for this process only; broadcast identity/cursor persists independently of attachment. A detach or full delete suppresses an environment declaration only until restart. Remove that declaration to keep it absent after restart.

Goals are bounded, cancelable fetching; explicit SSRF policy; exclusive production across pull/raw PUT/RTMP; durable allocation before publication; owned deletion/shutdown; and private source status. Failure must never silently reuse a published piece index within the approved platform guarantee, publish after deletion, or leak a credential-bearing URL. The approved Windows guarantee protects process restarts while OS/filesystem state survives; it does not cover system crash or power loss.

Non-goals: UI, source playlists/HLS, transcoding/remuxing, codec detection, bitrate detection/configuration, descriptor geometry changes, metadata/tracker expansion, source authentication headers/cookies, durable API job specifications, Range resume, general daemon task-framework replacement, or public-source testing. Retain existing seeding limits, cache settings, bind defaults and tracker behavior. Accept only the public, unencrypted origination scope already supported by the repository. Seamless TS timestamps/PAT/PMT continuity across upstream restarts is not guaranteed.

## Evidence and alternatives

This design uses the private audit and original-source research dated 2026-10-23 and reads the current `broadcast.rs`, `broadcast_ingest.rs`, `broadcast_persist.rs`, HTTP handlers/state, RTMP handler, runtime/config, signing chunker, TS resynchronizer and transport URL fetcher. No probes or checks were executed. The original engine documents HTTP MPEG-TS origination, reconnects, and separately reusable signing/piece metadata. The research does not establish automatic reload of API-created source jobs. Outpace's restart contract above is a product choice, not a parity claim. Relevant references are the official [source parameters](https://docs.acestream.media/broadcasting/reference/#mpeg-ts-source-node-parameters) and [source-node relocation](https://docs.acestream.media/broadcasting/administration/relocating-the-source-node/).

Three approaches were considered:

1. **Selected: one pull worker plus an entry-owned controller and exclusive producer session.** Reuses `BroadcastIngest → SigningChunker → PieceStore → SeedRegistry`; adds a small HTTP worker and guarded fetch helper. Requires explicit lifecycle/persistence serialization but minimizes changes to existing ingress.
2. **Per-broadcast actor for all ingress/lifecycle commands.** Naturally orders callbacks and writes, but adds channels, queue/backpressure behavior and a broader PUT/RTMP rewrite. Disproportionate for #206; do not introduce it incidentally.
3. **Worker with durable API source specifications.** Improves unattended API recovery but introduces secret storage, declaration precedence and durable detach semantics. Rejected for this scope in favor of the selected process-local API contract. This persistence choice is independent of actor versus worker.

Current `start_or_resume` is infallible; separate ingests snapshot the same cursor; output advances that cursor only after storing chunks. Cursor checkpoints lag by 128 pieces and rename without syncing. Repeated short crashes can therefore reuse an index. DELETE does not join ingress, and announcement handles are discarded. These shared-path defects must be corrected to support automatic pull retries safely; merely adding a fetch loop is insufficient.

## Typed configuration and admission

The configuration values and bounds in this document are part of the approved design.

Add these fields to serde-defaulted `Config`:

```rust
pub broadcast_sources: BTreeMap<String, BroadcastSourceConfig>, // default empty
pub allow_non_global_broadcast_source: bool,                  // default false

#[derive(Clone, Deserialize, Serialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct BroadcastSourceConfig {
    pub url: String,                       // required; never derived Debug
    #[serde(default = "default_connect_timeout_secs")]
    pub connect_timeout_secs: u64,          // 5; range 1..=60
    #[serde(default = "default_read_timeout_secs")]
    pub read_timeout_secs: u64,             // 15; range 1..=300
    #[serde(default = "default_reconnect_initial_secs")]
    pub reconnect_initial_secs: u64,        // 1; range 1..=300
    #[serde(default = "default_reconnect_max_secs")]
    pub reconnect_max_secs: u64,            // 30; range 1..=300
}
```

Use a validated internal form holding the parsed URL and `Duration`s. Do not give `url` a default. Reject null/float/negative durations, zero, out-of-range values, unknown fields and initial greater than maximum. Source config and enclosing config Debug output must redact source URLs. Do not derive a URL-bearing Debug representation indirectly through the map.

`OUTPACE_BROADCAST_SOURCES` is one JSON object mapping names to the above objects; absent means `{}`, while empty/malformed text is an error. Proposed limits: 256 KiB UTF-8 input, 64 entries, duplicate object keys rejected, and each URL at most 8,192 bytes. Names use shared `valid_broadcast_name`: 1–64 ASCII letters/digits/`.`/`_`/`-`, excluding `.` and `..`. Validate the entire map before runtime side effects. Programmatic `Config` passes the same validation in `build_runtime`; env parsing must not be the only gate. No general config-file loader is added.

`OUTPACE_ALLOW_NON_GLOBAL_BROADCAST_SOURCE` enables the corresponding field only for the exact string `1`; unset and all other strings deny. It is operator-only, never a field in the source request. Existing transport and tracker opt-ins retain their independent scopes. Do not consult those switches to authorize a source.

URL admission requires an absolute `http`/`https` URL, nonempty host, effective port 1–65535, no userinfo (including empty userinfo syntax), no fragment, and no control characters. Query tokens are allowed and kept private. Reject disallowed literal IPs synchronously as `source_address_blocked`; hostname DNS/policy decisions occur in the worker. Do not resolve DNS during admission. Validate before minting a broadcast or claiming a producer. Error messages identify a field/code without including rejected text.

Idempotency compares the validated parsed URL's serialized form and all default-filled timing values. Standard URL parser normalization applies (including host case/default ports); path/query order and token values are otherwise significant. Do not reorder query parameters or infer equivalent resources. There is no idempotency token, source replacement, custom method, or partial-update schema.

## Native API contract

Add `/broadcast/{name}/source` beside the existing raw route, independent of Ace compatibility mode. It uses the same native API exposure/authentication policy as current broadcast mutation routes; #206 adds no listener or authentication framework. New source requests have a 16 KiB body limit and require JSON. Normalize extractor failures into the error contract below.

| Request | Success and behavior |
| --- | --- |
| `PUT /broadcast/{name}/source` | `202` JSON `{name, content_id, infohash, source}`. Validate, exclusively admit, durably create/resume identity and initial reservation, then schedule one worker. Acceptance does not mean upstream health. An identical attached config returns `202` with current state, without resetting attempts, duplicating announcements or restarting even a failed worker. Different config or another producer returns `409`; detach before changing it. |
| `GET /broadcast/{name}/source` | `200` JSON `{name, source}` for an attachment, including blocked/failed/stopping attachments; `404` when detached or unknown. Does not mint anything. |
| `DELETE /broadcast/{name}/source` | `204` after cancellation and worker join, or when already detached/unknown. Retains descriptor, signing identity, seed lease/store and announcers; permits a subsequent producer. Concurrent identical deletes join the same stop operation. |
| Existing `GET /broadcast/{name}` | Preserve binary transport bytes and existing content type/unknown behavior. No JSON source fields are added. |
| Existing raw `PUT /broadcast/{name}` | Preserve immediate `200` JSON `{name, content_id, infohash}` and streaming-body behavior. Add shared admission/persistence errors and exclusive producer conflict. |
| Existing `DELETE /broadcast/{name}` | `204` only after all ingress and announcements stop, seed lease is dropped and persistent identity deletion is durable; unknown is idempotent `204`. Subsequent admission mints a new identity. |

For source routes, validate names first (`400`), then reject disabled broadcast support (`404`), shutdown (`503`) and per-name stopping (`409`) before changing state. A source detach must not stop a raw PUT/RTMP producer. Its absence is `204` in that case. Full deletion stops any producer. During full deletion descriptor GET returns `404`, source GET may return `stopping` until the attachment is removed, and new producer admission returns `409`.

Source-route and newly introduced mutation failures return `application/json` with exactly `{"error":{"code":"..."}}`, without underlying error text:

| HTTP status | Codes/conditions |
| --- | --- |
| `400` | `invalid_name`, `invalid_source_config` (including malformed/duplicate/unknown fields), `invalid_source_url`, `source_address_blocked` (literal address) |
| `404` | `broadcasts_disabled`, `source_not_found` |
| `409` | `producer_conflict`, `source_conflict`, `broadcast_stopping` |
| `413` | `source_request_too_large` |
| `415` | `source_content_type_required` |
| `500` | `broadcast_persistence_failed`, `broadcast_state_invalid`, `piece_index_exhausted` |
| `503` | `broadcast_service_stopping`, `broadcast_cleanup_timeout` |

Keep legacy successful response shapes/statuses; full DELETE must now expose disk/cleanup failure instead of silently returning success. RTMP uses equivalent fixed `AuthResult::Reject` reasons for invalid names, conflicts, stopping and persistence failure; it has no HTTP status. Do not reject with a raw error string.

The `source` object has exactly `state`, `attempts`, `last_error`, `retry_in_ms`. State is one of `connecting`, `streaming`, `backoff`, `blocked`, `failed`, `stopping`. `attempts` is a saturating `u64`, initially zero, incremented when a connection attempt starts (including DNS). `last_error` is nullable and drawn only from the codes below; clear it on the first aligned TS output of a new successful attempt. `retry_in_ms` is nullable and is the remaining monotonic delay only in `backoff`/`blocked`. State becomes `streaming` on aligned TS progress, not merely on receiving headers.

Retryable sanitized codes: `dns_timeout`, `dns_failed`, `address_blocked`, `connect_timeout`, `connect_failed`, `tls_failed`, `headers_timeout`, `redirect_rejected`, `http_status`, `unsupported_response`, `body_failed`, `body_frame_too_large`, `read_timeout`, `progress_timeout`, `upstream_eof`. Terminal codes: `persistence_failed`, `piece_index_exhausted`, `ingest_failed`, `worker_failed`. A request accepted before an asynchronous disk failure remains accepted; report `failed` without automatic retry. Detach/reattach requests fresh admission, but a poisoned persistence generation still rejects it until safe reload on daemon restart or successful full deletion. Keep the pull producer claimed while failed to prevent implicit takeover.

No status field returns URL, host, address, path/query, credentials, upstream body, HTTP reason text, persistence path, signing key, or debug/error chain. Identity fields in PUT are the existing generated runtime metadata; do not add them to logs. Use `alog!("[broadcast] ...")` with validated name, state and fixed reason codes only. Never format reqwest/URL-bearing errors or invalid source settings. Log transitions/retry failures at most once per source per 30 seconds, with a single terminal event; no per-body-chunk logging.

## Guarded HTTP streaming and SSRF

Extract the existing transport URL address policy and reqwest construction into small `ace-swarm/src/http_fetch.rs`, exported by `lib.rs`. Keep reqwest/rustls dependencies there. Expose an explicit `FetchPolicy`, typed sanitized fetch errors, per-attempt open/stream operations and a narrow `next_chunk` adapter; the engine supplies policy and deadlines. No environment reads inside shared policy. Transport wrapper maps its existing opt-in to policy and retains its 1 MiB body ceiling, 5-second connect and 15-second finite request deadline. Source streaming has no total lifetime/body-byte ceiling. Explicit proxy disabling also hardens that shared transport builder; document this small existing-fetch behavior change.

Preserve the current denylist rather than claiming full IANA global-address classification. Default denies IPv4 private/loopback/link-local/unspecified/broadcast/documentation/multicast and CGNAT, and IPv6 loopback/unspecified/multicast/ULA/link-local; mapped IPv4 uses the IPv4 rule. The source opt-in adds only private/loopback/CGNAT IPv4 and IPv6 ULA/loopback and mapped equivalents. It never unblocks link-local (including metadata services), unspecified, multicast, IPv4 broadcast/documentation. Other special ranges retain the current classifier's behavior; expanding that policy is separate work.

Each attempt constructs a fresh nonpooled-across-attempts client/response:

1. Normalize bracketed IPv6 hosts, validate IP literals directly or resolve the hostname with a fixed 5-second DNS deadline. Inspect candidates and choose the first permitted address; mixed answers may use an allowed candidate. If none is allowed, set `blocked`/`address_blocked` and do not dial. Re-resolve/revalidate on every retry; never retain a previous allowed answer as fallback to a newly blocked resolution.
2. Pin the chosen host/address with `.resolve(host, addr)`, with no alternative resolver/dial fallback. Preserve the original URL hostname for Host, TLS SNI and certificate verification. New attempts may select another validated address; a single attempt dials only its chosen address.
3. Set `.no_proxy()` explicitly (including environment proxies), disable redirects with `Policy::none()` and hidden request retries with `.retry(reqwest::retry::never())`, retain bundled TLS roots/ring and ordinary certificate/hostname verification. No unsafe TLS setting, production trust injection, cookie jar, forwarded client headers, referer, or URL-derived authorization. Do not request compression; reject non-identity Content-Encoding. Never follow a redirect, including same-host/public targets; drop its body without dialing Location. Only the worker schedules another source attempt.
4. GET the entire resource with no Range/conditional headers. Accept successful body-bearing 2xx responses except `204`, `205` and `206`; reject upgrades, Content-Range and unexpected partial semantics as `unsupported_response`. Other non-2xx codes become `http_status` (3xx becomes `redirect_rejected`). Missing/generic Content-Type is acceptable; no MIME allowlist substitutes for TS progress.
5. Header/open completion has an overall fixed 15-second deadline starting after DNS; connection/TLS establishment also has configured `connect_timeout_secs`. The earlier limit wins, so a configured connect timeout over 15 seconds does not extend header wait. Proposed source client uses `.http1_only().http1_max_headers(64)`. The locked reqwest 0.13.5/Hyper 1.11.1 parser already bounds its HTTP/1 read buffer to 417,792 bytes; retain that finite parser bound, then reject parsed header-name/value bytes totaling over 32 KiB before consuming body. The latter is an acceptance bound, not a preparse allocation claim. Map known header-size/count failures to `unsupported_response` (other open errors may be `connect_failed`). This needs no new HTTP stack; preserve transport wrapper's existing protocol preferences. Reassess the parser bound when updating those dependencies.
6. Consume sequentially with backpressure: one response read and one ingest call at a time, no unbounded channel, whole-body collection, or lifetime byte counter cap. Engine feed slices are at most 64 KiB; reject an adapter-returned body frame over 256 KiB before retaining/feeding it and report `body_frame_too_large`. Keep at most one accepted frame, resync tail, one signing payload and one slice's output vector. This bounds application-retained buffers, not all HTTP/TLS allocator internals. Content-Length does not cause preallocation. A finite Content-Length ending cleanly is still a live-source EOF and retries.

Use explicit cancellation selection for DNS, connect/header future, each body read, ingest/store-lock wait and backoff. Dropping an attempt drops response/client and closes its socket. No whole-stream request timeout; a healthy live stream may run indefinitely.

## Progress, reconnects and tails

Proposed fixed policy constants: DNS 5 seconds; headers 15 seconds; no-aligned-progress 30 seconds; local ingest operation 15 seconds; healthy-reset window 30 seconds; cleanup grace 5 seconds. These are not additional public settings. Body idle uses configured `read_timeout_secs`, measured between nonempty body data while waiting for the upstream; empty frames do not reset it. The 30-second progress deadline starts at accepted headers and resets only when `TsResync` emits aligned TS bytes. It runs across successive reads, so a trickle of HTML/junk cannot keep a source alive. It measures TS alignment, not codec decodability or minimum bitrate. Ingest returns a small progress count, avoiding a second resynchronizer in the worker.

Nonempty TS progress sets streaming; no-progress timeout still applies even when read timeout is configured longer. A 15-second local ingest/store/persistence-wait limit reports terminal `ingest_failed` (or `persistence_failed` when known), rather than retrying the upstream into a stuck local store. Retain the producer/stopping boundary while any noncancelable disk work finishes; the timeout never authorizes a competing writer.

On DNS/connect/TLS/header/HTTP/body/idle/progress failure or EOF, drop the attempt's resync/signing buffers. **Do not call `finish()` for pull EOF, retry, detach, shutdown or errors.** Full signed pieces already published remain. In-memory next piece advances past every piece whose first chunk was exposed, even if a later chunk/store operation fails; never retry an exposed index. Any interrupted exposed piece is skipped on the next session; do not splice its bytes into the new connection. A fresh `BroadcastIngest` starts at the shared next cursor for each attempt. No Range replay or same-connection tail reuse. An upstream may repeat bytes after reconnect, but they receive new indexes.

For failure number `k` since healthy reset, base delay is `min(max, initial * 2^k)`, beginning with `k=0`; use checked/capped arithmetic. Sample integer milliseconds uniformly from `[ceil(0.9 * base_ms), base_ms]`, keeping the configured maximum a hard ceiling. All retryable outcomes, including immediate EOF, have this delay; no tight loop. Policy denials use `blocked` while waiting, other failures `backoff`. Retry indefinitely until canceled, permitting DNS/upstream recovery; static invalid settings never reach the worker. A connection resets `k` only after at least 30 seconds of streaming with no 30-second progress timeout and at least one complete committed piece. HTTP 200 or one aligned packet alone does not reset backoff. Retry timing and jitter have injectable clock/RNG seams for synthetic validation.

Preserve finite ingress explicitly: raw PUT on ordinary EOF/body termination and RTMP on ordinary unpublish still call the existing finite `finish()` exactly once, including its possibly short signed final piece. Continue the existing TS resync, RTMP mux and 65,536/16,384 geometry; do not change finite tails to fix live reconnection. `finish()` becomes fallible, reserves before publishing and seals that ingest instance against later pushes. Cancellation by delete/shutdown and fatal persistence failures drop tails instead. Finite tails retain their existing fixed-geometry reassembly limitation; #206 does not make them playable by a full-piece-only consumer.

## Exclusive producer and durable piece allocation

Keep `BroadcastEntry` as owner of the noncloneable `SeedLease`. Add a per-name lifecycle/controller with monotonic generation, `open/stopping/closed` state, optional producer session, optional source attachment/status, owned ingress/announcement handles and serialized persistence gate. This is entry state, not an actor/command framework. Short map locks find/create the controller; never hold the global map lock during network, filesystem or joins. Per-name stop placeholders remain visible while work completes, preventing same-name recreation races.

The registry exposes fallible asynchronous admission rather than allowing routes to call infallible `start_or_resume` and then independently create ingest. Concrete proposed interface roles:

```rust
enum ProducerKind { RawPut, Rtmp, Pull }
// Names illustrative; error semantics and ordering are required.
async fn acquire_producer(/* validated name, mint params, kind */)
    -> Result<(Broadcast, ProducerSession), BroadcastError>;
async fn push_bytes(&mut self, bytes: &[u8]) -> Result<IngestProgress, IngestError>;
async fn finish(&mut self) -> Result<(), IngestError>; // finite ingress only
```

`ProducerSession` carries generation/cancellation and exclusive authority; `BroadcastIngest` must require it for production construction. Diskless/test constructors are explicit and never silently used after a disk failure. Competing raw PUT, RTMP or pull admission is atomic and returns conflict, without consuming/minting another identity. The pull claim spans connecting, streaming, backoff, blocked and failed. Sequential producers keep the same descriptor/key and continue allocation; different names remain concurrent. Every publish path checks generation/cancellation under the same publication gate immediately before exposing chunks.

Replace checkpoint safety with exclusive durable high-water reservations, block size 128 pieces. Keep actual in-process `next_piece` separate from `reserved_until` (exclusive). Add optional `reserved_until: u64` to the existing JSON record; absence denotes legacy format. For a new record start at zero; before successful producer admission persist identity and reservation `[0,128)`. When a piece would be outside the reservation, durably extend by enough 128-piece blocks before publishing its first chunk. A single input can emit multiple pieces: cover all indexes or reserve each before its first publication. Checked additions, including `piece + 1`, fail closed at exhaustion.

Publication ordering is: verify active generation/session → ensure durable reservation → consume the index by raising actual next to at least `piece + 1` → recheck cancellation/generation under publication gate → expose chunks. Reservation/persistence failure exposes no chunk from the uncovered piece and is propagated to admission/ingest. Once an index is consumed it cannot be reclaimed, including after cancellation or partially successful store output. The session prevents another producer using an in-memory reservation concurrently. Reservation success is recorded in memory only after durable save completes; uncertain write failure poisons this generation's publishing state until reload or full deletion.

On reload of a new-format record, begin at `reserved_until`, not saved actual next, then durably reserve the next block before any producer succeeds. Repeated restart-without-finish therefore skips a different durable interval each time. Persisted actual `next_piece` is diagnostic only; every save/finite flush retains or increases `reserved_until`. Reject a record with next greater than reservation or arithmetic/identity/transport/key mismatch. Distinguish absence from unreadable/invalid records: do not silently re-mint over an existing record. Such a name fails closed with `broadcast_state_invalid`; startup may continue serving other valid names, but must report that name safely and prevent lazy re-minting.

For legacy records, calculate `start = old next_piece + 128` with checked addition and durably migrate to `next_piece = start, reserved_until = start + 128` before any new publication. This cannot retroactively fix reuse by old versions; it prevents adding a new migration reuse window. Do not write a migrated reservation and then resume from the legacy next on a different path. Graceful finish may checkpoint actual next for diagnostics but cannot reduce the durable high-water.

The strong durability target is private temp creation (Unix mode 0600), complete write, file `sync_all`, atomic replacement on the same filesystem and parent-directory persistence, including newly created state directory links. A save/delete is successful only after the operations required by its approved platform guarantee succeed. Keep key material private on supported platforms. Serialize saves/deletion by identity generation with unique generation-specific temporary names; run blocking filesystem work off Tokio worker threads. On any required operation's failure return an error, clean temporary files when possible and never advance a success checkpoint speculatively. Do not label rename/file flush alone as equivalent to durable namespace persistence.

### Platform compatibility decision — approved

Existing releases include Linux, macOS and Windows; runtime uses persistent broadcasts for existing PUT, RTMP and CLI minting too. The user approved preserving existing supported origination with explicitly documented per-platform guarantees. A universal system-crash/power-loss claim is not established on Windows by the bounded primary-source review. The rules in this subsection qualify uses of “durable” throughout this approved design.

**Approved smallest approach:** keep the JSON reservation format and serialized save/delete gate; implement a small platform-specific persistence boundary, and document the guarantee per platform. Use exclusive same-directory temp creation, complete write, checked `File::sync_all`, same-filesystem replacement and checked deletion everywhere. On Linux, additionally sync affected directories and new directory links before acknowledging; the [Linux `fsync` manual](https://www.man7.org/linux/man-pages/man2/fsync.2.html) explicitly requires directory sync for namespace persistence. On macOS, the [pinned Rust implementation](https://github.com/rust-lang/rust/blob/1.99.1/library/std/src/sys/fs/unix.rs) uses `F_FULLFSYNC` for file `sync_all`; use the existing direct `libc` dependency for directory `fsync` rather than assuming Rust's full-sync operation is interchangeable on directory handles. [Apple's documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html) distinguishes host flushing from drive-cache flushing. Do not infer an all-filesystem power-loss guarantee from the OS name or a successful file flush; unsupported directory/drive semantics need an explicitly documented guarantee boundary, not blanket removal of existing ingress.

On Windows, the approved contract preserves persistent PUT/RTMP/CLI and adds pull using acknowledged file-sync/replacement ordering, with a documented **process-crash/ordinary daemon restart guarantee while the OS/filesystem state remains intact**, not a system-crash/power-loss guarantee. Do not require directory sync there or swallow actual file-write/sync/replacement/delete failures. A system crash/power loss could roll back a reservation and reuse published indexes under a surviving identity, lose an identity, or resurrect a deleted record. The user explicitly approved this narrowing of the strong target, including the full-DELETE durability promise. The same limitation must be explicit for any other filesystem where the stronger sequence is not established. An undetectable stale but valid record cannot be repaired by reload validation or simply skipping one extra block.

The evidence does not establish an equivalent small Windows native replacement: [Rust's Windows implementation](https://github.com/rust-lang/rust/blob/1.99.1/library/std/src/sys/fs/windows.rs) uses `FlushFileBuffers` for `sync_all` and a rename path without a write-through flag. [`MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) describes write-through completion and specifically a flushed copy/delete move; that is not evidence for the complete same-volume replacement, directory-creation and deletion protocol required here. [`ReplaceFileW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) does not support its write-through flag. [`CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents write-through NTFS metadata effects for the request being processed; it does not by itself establish the entire multi-operation protocol. [`FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) documents volume flushing with administrative privileges; making that an origination prerequisite changes deployment requirements. Neither a new Windows API binding nor locked transitive `tempfile`/`windows-sys` supplies a durability proof; `tempfile` explicitly leaves file/directory synchronization to its caller.

**Resolution:** the user selected and approved the documented per-platform guarantee while preserving existing supported origination. No equivalent Windows system-crash/power-loss guarantee or additional native persistence research is required for #206. Do not introduce a journal/database redesign, require elevated Windows execution, disable existing PUT/RTMP/CLI, or weaken the approved ordering and error propagation.

Blocking filesystem syscalls cannot reliably be canceled. The owned persistence gate/work handle remains until they settle, even when a caller's wait times out; cancellation prevents their result from authorizing publication. Deletion waits behind that gate, so an already-started save cannot recreate a deleted identity. If it cannot settle within cleanup grace, retain a nonadmitting stopping placeholder and return `503`, rather than claiming deletion or permitting recreation. A serialized deletion continuation may complete later; repeated DELETE joins/observes it. Record deletion completes the namespace persistence operations required by the approved platform guarantee above; on disk failure retain stopping state and return `500` until an explicit delete retry succeeds.

Forward gaps of up to the unconsumed reservation, plus abandoned pieces, are intentional. Guarantees assume one daemon exclusively owns its data directory and storage honors sync/rename; copying/restoring old state, concurrent processes sharing it and older binaries are not covered. Older binaries ignore `reserved_until` and retain the unsafe checkpoint scheme. Do not roll back a persistent active broadcast under the same identity: retain the new binary, or stop it, remove the identity deliberately and publish a fresh one after rollback. Restoring an old backup of signing/cursor state can reuse indexes; documentation must state this limitation.

## Ownership, deletion and runtime lifecycle

The controller owns source cancellation sender plus JoinHandle; workers hold only session/store/auth/cursor/status handles, never a strong controller/registry reference creating a cycle. Use existing Tokio watch cancellation and owned handles; do not introduce a cancellation dependency or general task supervisor. Concurrent identical attach/detach/delete operations serialize per name. A canceled attach request must not leave a claim without an owned worker: once committed, ownership is service-local and independent of request lifetime.

Track raw PUT tasks too. RTMP stream state must be keyed/checked by publishing session and generation, not merely a reusable string key: an old media/unpublish callback must not remove/reinsert/finish a replacement stream. Use a per-session async mutex for mux+ingest and a short map lock only to clone/remove its handle; recheck active generation before ingest/reinsert. Reject a second publisher instead of replacing its map entry. Shared name validation on the exact RTMP key (no whitespace trimming) replaces the empty-only check. Deletion cancels the broadcast session and waits for its in-flight mux/ingest/finish operations to settle through the session operation barrier, joining any broadcast-owned tasks; callbacks queued behind that barrier recheck cancellation/generation and become no-ops. This waits for broadcast ingest operations, not for the enclosing RTMP connection task or socket to end. Release a producer only after cleanup, never when a callback temporarily removes a value to await. Raw/RTMP asynchronous ingest failures stop that session and log a fixed code; a prior successful raw admission response cannot be retroactively changed. Outstanding persistence retains its fence even after ingress ends.

RTMP cleanup acceptance is **broadcast-operation quiescence and fencing**, plus stopping/joining the owned listener during runtime cleanup. Installed `rtmp-rs` 0.6.0 `run_until` stops its accept loop and aborts its registry cleanup task; its established connection tasks are spawned without retained join handles. #206 must not require terminating/joining every established RTMP connection, vendor the dependency, or redesign that server framework. Those connections may remain alive after broadcast cleanup; later callbacks cannot publish, finish a canceled tail, save, recreate an attachment or mutate a replacement session. Runtime admission closure also rejects new publish requests from already connected clients. Full delete fences its old session while permitting a later separately admitted session once deletion completes. Ordinary unpublish before cancellation still serializes and calls finite `finish()` exactly once; delete/shutdown cancellation drops the tail.

Source detach marks stopping, signals cancellation, joins outside map locks, drops response/partial state, then removes the attachment and releases its producer. It keeps the entry/lease and announcers. A terminal failed worker is still an attached source and must be detached explicitly. Full delete first marks the generation stopping and fences publication/admission, cancels every producer and announcer, joins their broadcast work/persistence (using the RTMP operation barrier above), durably deletes identity, drops the SeedLease and closes/removes the entry. Stale clones cannot publish or save after closure. Disk cache cleanup follows existing store/lease ownership after references are released; no seeder/wire redesign is needed.

Own the two existing identity announcement loops per entry and use one idempotent `ensure_announcing` path for fresh mint, startup reload and CLI. A pull retry never creates new loops/leases. Wrap the existing announcement future in cancellation selection so cancel drops its in-flight network work; do not rely on port-watch closure, which currently parks. Source detach retains announcements since cached identity/data remains servable; full delete and runtime shutdown stop/join them. Preserve current no-inbound behavior. Do not add tracker/DHT policy, network calls or announce metadata.

`build_runtime` validates source settings and reconstructs persisted identities, but starts no source readers or broadcast announcers. The service is owned through `EngineRuntime`/`BroadcastState`. In `serve_http_inner`, establish the HTTP listener and start the existing RTMP service with owned lifetime before attaching configured sources/starting broadcast announcements. A source URL being temporarily down/blocked does not fail startup; invalid configuration does. A local configured-source identity/reservation failure fails startup and unwinds already started broadcast work. Keep established RTMP listener error behavior except for retaining/stopping its handle; do not rewrite its server framework merely to prebind it. Configured attachments use the same admission path in deterministic name order before accepting API traffic, so startup cannot race API claims.

On signal, close broadcast admissions and cancel producers/read/backoff/announcers **before** HTTP graceful draining; otherwise a live body can hold drain indefinitely. Apply a shared 5-second broadcast cleanup grace, abort and join leftover broadcast-owned async tasks, settle/fence RTMP broadcast operations through their session barriers, and retain fences for any outstanding blocking persistence operation. This does not require aborting/joining dependency-owned established RTMP connection tasks. Unsettled broadcast operations retain stopping state and report cleanup failure under the same timeout rules. On normal server return and every listener/startup error run the same cleanup, including already attached configured sources and the owned RTMP listener. The `serve_http` wrapper must still call existing `StreamManager::shutdown()` for HLS cleanup on success and error. Scope cleanup changes to broadcasts and the touched RTMP lifetime, leaving unrelated runtime tasks alone.

If persistent I/O remains stuck, bounded async shutdown can report failure and prohibit further publication but cannot promise cancellation of the OS syscall or immediate Tokio blocking-pool/process exit. Do not detach such work and claim successful durable deletion. Shutdown preserves identity/reservations, drops pull tails and does not persist source URLs. On next startup only current environment declarations reattach; API sources remain detached even though their descriptors can still be served. CLI `broadcast` reuses the owned mint/announce path; it does not gain a separate source flag in #206.
