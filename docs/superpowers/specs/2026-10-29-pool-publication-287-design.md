# Issue 287: bounded accepted-piece publication responsiveness

Status: user-approved implementation, integration coverage and independent review are complete; publication and CI remain pending. #287 and v0.9 remain open; release is premature. Scope is the pool actor/publication boundary only. Reciprocal reads, activation awaits and output-channel backpressure require separate acceptance. Source anchors:
- live_session/pool/actor.rs: run checks consumer closure at loop boundaries; on_piece around 661–735 verifies/completes, borrows completed wire, then awaits shared_put_complete_piece outside select. Only afterward does it account receipt, drain contiguous output and schedule requests. Other events cannot run during that await.
- store.rs:213–291 validates geometry under the async mutex. Memory publication copies chunks and updates metadata synchronously under that guard. Disabled/undersized cache returns NotRetained. Disk clones a handle and releases the mutex before disk admission/completion; afterward it reacquires the mutex to refresh cur_bytes.
- store/disk.rs: PendingWire drops its Vec before returning its permit; DiskHandle::put_complete acquires the shared sole permit BEFORE copying. Actor::run drops PendingWire after put_complete succeeds/fails and before sending its oneshot result. put_complete checks immutable existing completion, writes a temporary file, renames, publishes index and performs eviction before acknowledgement. A cancelled receiver does not cancel the command.
- ace-wire/reassembly.rs: complete buffers are immutable to duplicates; completed_live_piece borrows full wire including signature. add_live_chunk reports completed only on the transition, not duplicates. take_ready removes ALL contiguous complete pieces without publication awareness. skip_to deletes completed and partial buffers below its target. max_ahead bounds admitted indices relative to next_emit, NOT lifetime completion count. These cannot be left untouched by a retention design.

The independently approved receipts establish two finite behavioral RED observations: a generated accepted RSA whole piece reaches the disk precommit gate holding 848 pending wire bytes and zero free publication permits; unrelated Interested→actor Unchoke and actual consumer-close→pool Join each fail to progress within 250 ms. Release restores progress and drains the owned command. This is not proof of infinite deadlock, historical cause, live-player impact, or a 250 ms production SLA. The pending-byte counter excludes reassembly and all other process memory. Review qualifies remote teardown as read-error witnesses, not explicit private-worker joins.

## Recommendation and alternatives

Recommend an actor-owned publication state machine with explicit store admission and command-result tickets. Retain original accepted bytes in the existing bounded reassembler; do not move them into a generic background worker. One actor operation at a time, one outstanding owned full-wire command per shared disk STORE, no new tasks or channels. Carry publication ledger metadata in Continuity so ordinary pool reconnects cannot accidentally emit retained unacknowledged pieces.

Alternative: a single local future borrowing completed wire while selecting control events. This avoids a new admission API, but the borrow prevents mutating Continuity/reassembly through current control, skip and request paths. Re-entering arbitrary actor methods creates overlapping mutable borrows; moving the actor into the future or capturing self creates the wrong ownership. A dedicated nested loop with individually split fields could work, but duplicates #284 dispatch/lifecycle logic and still needs publication-aware cursor gates. Reject for this boundary.

Alternative: move completed buffers to a bounded publisher task/channel. It can be correct with explicit capacity and joined lifecycle, but requires extraction/reinsertion, separate contiguous playback ownership, cancellation and generation protocols, and accounting buffers outside the reassembler's moving window. A spawned task per completion or unbounded queue is unacceptable. The explicit-ticket design reuses the existing disk actor and has fewer owners.

These are recommendations, not claims that the user already selected an implementation.

## Concrete interfaces and owners

Names below are proposed internal interfaces, not existing APIs.

store.rs adds a store-private whole-publication protocol used by the pool and by the existing shared_put_complete_piece wrapper:

1. begin_complete_admission(store: Arc<Mutex<PieceStore>>, piece: u64, wire_len: usize) -> owned Future<Result<CompleteAdmission>>. This future owns only Arc handles, lengths and metadata; never wire bytes or a reassembler reference. It first uses lock_owned to validate the exact existing geometry and retention eligibility. Result is either Immediate(CompletePut), Memory(OwnedMutexGuard<PieceStore>, validated geometry), or Disk(DiskReservation). For disk it snapshots the existing configuration, clones the handle, drops the store guard, then awaits acquire_owned on the SAME backend semaphore. DiskReservation owns that permit and validated geometry. Do not create a new semaphore per actor/generation. Store backend/config replacement during admission must remain unsupported as today; if source inspection during implementation finds mutable configuration used concurrently, revalidate with an explicit revision token before submit rather than guessing.
2. CompleteAdmission::submit(self, piece, header, wire: &[u8]) -> Result<PublicationReceipt>. No await. Validate wire length again. For Memory, perform the same atomic chunk-copy/index/eviction operation under the owned guard, returning Ready(result). For Disk, construct PendingWire only NOW, copy once, transfer permit + Vec into Command::PutComplete and return Awaiting(oneshot Receiver<Result<CompletePut>>). Failed send drops the command/Vec/permit. The returned receipt owns no wire and no actor borrow. An unused reservation drops its permit without allocating wire.
3. Keep shared_put_complete_piece as the compatibility wrapper over this protocol; it borrows caller wire across admission, submits, awaits result, then retains its existing accounting-refresh behavior. Avoid a second parallel publication implementation.
4. For actor receipts, the existing disk cur_bytes refresh must not introduce a hidden exclusive mutex await after acknowledgement. Use a separately selected lock_owned refresh phase with no wire copy, or make disk retained-byte queries authoritative everywhere they currently depend on this mirror. Prefer the former, smaller change: result is not processed as terminal until refresh finishes. No store guard across disk admission or acknowledgement. Memory's synchronous copy under its obtained guard is finite work, not an awaitable disk job; it does not imply a hard real-time latency bound for arbitrarily large pieces.

store/disk.rs splits current put_complete into admission/reservation and synchronous enqueue, retaining PendingWire, Command::PutComplete, actor commit and ack order. Reservation types stay private behind store.rs; callers cannot accidentally copy before acquiring. Existing trusted chunk APIs are unchanged and are not included in the one-whole-wire-command proof.

Continuity (definition in live_session/mod.rs, methods in continuity.rs) owns a BTreeMap<piece, PublicationStatus> with Needed or Terminal(result classification). Entries only accompany retained complete pieces. Needed covers both not-yet-admitted and actor-in-flight; do NOT persist an InFlight mark that could survive a cancelled actor. Header and bytes remain solely in reasm. No Vec in the ledger. Eligibility is established only from completed_live_piece's accepted variants. Completion lacking publication geometry or with Unauthenticated acceptance retains existing playback semantics and is not converted to cache publication.

PoolActor owns Option<PublicationOperation>: Acquiring { piece, owned boxed admission future }, Awaiting { piece, result receiver }, or Refreshing { piece, result, owned lock future }. No operation captures self or borrowed Continuity. At most one operation. Initialization of PoolActor in pool.rs includes empty operation; it scans retained Needed entries before any output after reconnect. The actor resumes an unacknowledged piece by re-admission; the store's immutable AlreadyPresent handling makes cancellation after commit safe, without relying on a lost ack.

ace-wire/reassembly.rs may expose a bounded complete-index query (iterator, no wire copy) or actor-visible complete predicate. Keep legacy take_ready unchanged. This design uses a full finite-batch hold: the pool must not invoke take_ready while any Needed entry or active operation exists; after all attempts terminate it uses the existing ordered output path. No prefix-extraction API or opportunistic prefix emission is required. Ledger entries are removed after cursor advancement or explicit allowed skip. Retain existing trailer removal and complete-buffer immutability.

## Transitions, hold and further completion

On a real completion: record producer contribution and receipt accounting immediately; register Needed once for accepted publishable wire. Do not wait to note_chunk until disk completion. Duplicates remain immutable no-ops and cannot start another job or replace producer attribution. Do not reconstruct received_chunks entries indefinitely for already complete duplicates; preserve request receipt semantics by releasing applicable scheduler slots without retaining duplicate-only chunk maps.

A publication hold is true whenever any Needed entry or active operation exists. Before any possible cursor movement, install that hold in Continuity. Under hold:
- Continue receiving and processing every reliable event in original FIFO order. Add valid chunks within the FIXED current reassembly window; reject far-future/stale blocks by existing rules. Newly completed pieces get bounded Needed entries. No deferred PeerEvent queue and no stored chunk copies.
- Suppress new request selection, retransmission and all cursor advances: skip_far_behind_live (including its request_floor update), skip_evicted_gap, and resume's forward-gap skip. Keep peer-window/head/candidate observations current. Activation may use the frozen cursor; activation waits themselves remain outside acceptance. Methods must consult the same hold, including indirect calls from advance_pool_requests, on_refill and peer-loss handling.
- Freeze playback consumption while draining this finite batch (stronger and simpler than opportunistically emitting terminal prefixes). Existing in-flight chunks can finish; there are only W admissible indices. Select the lowest Needed index next. No completed accepted piece is silently evicted to make room for a moving window.
- Clocks/consumer close/peer loss still run. Existing stale timeout may end the pool instead of waiting forever. On stale or reconnect, ledger and reassembly survive as Continuity; a later actor services Needed before output or skips. No fresh pool bypass of the hold.

Admission readiness triggers synchronous borrow + submit. Acknowledgement/refresh sets that piece Terminal. After all Needed work drains, clear hold, emit eligible contiguous ready bytes with the existing resync/provenance/stats/output path BEFORE applying deferred head-based recovery on the following turn. Otherwise a newly advanced head could delete the just-published playback prefix. Then restore normal scheduling and recovery; remaining terminal ahead pieces may be discarded by ordinary explicit recovery. If no contiguous prefix exists, normal gap recovery resumes. Prune ledger with the reassembler's actual cursor.

No terminal cache failure automatically retries the same immutable completion forever. The current actor logs publication error and continues accepted playback; NotRetained also continues. Preserve this behavior: Terminal(Published), Terminal(AlreadyPresent), Terminal(NotRetained) and Terminal(ErrorLogged) all finish the publication attempt barrier. Successful cache publication must precede playback when publication succeeds; a pending command NEVER allows playback. Disabled/undersized caching and I/O failure have never guaranteed durable cache visibility before playback. Interpreting 'publication-before-playback' as requiring successful retention even in those cases would require a separate intentional policy change and approval. This design does not silently introduce fail-closed playback or pretend an error is a successful commit.

Index availability remains absent before successful atomic commit and complete afterward, subject to existing retention/byte eviction. A receipt is not a promise of permanent cache residency; another producer may evict it before playback. Playback uses its own accepted original buffer. AlreadyPresent keeps existing first-published bytes immutable, even if a later valid source completion differs. No raw signature tail is removed until playback extraction; stored wire remains exact.

## Event-loop fairness and intentional waits

A select branch alone is insufficient because pending_event can always win first. Each outer turn must check consumer closure first, and poll the owned publication operation at least once BEFORE draining a prepolled peer event. A ready operation advances at most one phase per turn; then process at most one reliable peer event before returning to the loop. Never await a pending publication phase exclusively. When no event is prepolled, include that phase in the existing select. Preserve the owned future across turns (do not recreate the semaphore acquire and lose FIFO waiter position).

Limit fairness changes to publication: explicitly poll its operation before the existing finite closed-event prefix, then retain the original wake select and per-peer FIFO ordering. Do not introduce a rotating scheduler for gossip/connect/discovery/refill/retry in this change. Existing stage-2 finite-prefix fairness reasoning remains; timer sweeps still happen at loop boundaries. Existing handler-specific awaits (reciprocal disk reads, activation, full output channel) can still delay a turn, and this design does not claim universal control responsiveness through those unrelated awaits.

Intentionally waiting: cache admission waits for the shared command permit without copying; playback waits for its accepted publication attempt to terminate; new requests and media cursor recovery wait behind the finite retained batch. Unrelated event processing and consumer shutdown must not wait for disk publication. Filesystem calls themselves remain unbounded OS operations; the design bounds actor ownership and progress opportunities, not disk completion time.

## Cancellation, teardown and generations

Consumer close returns ConsumerGone at the next actor turn even during admission/commit pause. Retire peers, gossip/connect resources and channels in the existing #284 order. Add the publication operation so its future/receiver/reservation drops without spawning, joining disk I/O, or touching actor state afterward. Cancelled admission owns no wire; cancelled reservation returns permit; cancelled receipt leaves the already-enqueued command completely owned by the disk actor. No callback can mutate Continuity after actor exit. Existing peer workers remain aborted according to existing ownership; do not claim new joins.

Continuity retains Needed for an unacknowledged operation and terminal records for acknowledged pieces. Next pool generation may acquire against the same store while the old command is paused: it owns NO copied wire while waiting. After drain it may submit an immutable duplicate, receiving AlreadyPresent, or retry a failed old command. A stale actor has no detached task/result path into the new actor. Final session drop releases retained reassembly/ledger; disk command still drains independently. No actor borrow or self-reference escapes. Store disk OS thread lifetime/join contract is unchanged.

## Memory argument and limits

Let W be the validated finite live max_reasm_pieces_ahead, P the piece wire length and C chunks per piece. Fixed cursor during unresolved publication admits fewer than/equal W distinct retained indices, with one P-byte Vec in either partial OR complete for each. Offset bookkeeping is at most C per well-formed live piece; ledger at most W small entries. Accepted buffer is retained, not additionally cloned for admission. The sole store semaphore bounds whole-publication pending owned wire to P for that store (or the validated size of its one admitted command). All generations/producers must share that semaphore. Pending counter stays tied to actual Vec lifetime, with Vec dropped before permit release, and result after both.

A waiting admission future owns store/handle/permit-wait state and identifiers only. It cannot contain Bytes/Vec copied from reassembly. This is stronger than 'one worker per actor': multiple generations waiting do not multiply owned wire. Existing event queues and one blocked worker event per peer remain separately bounded by configured peers/channel capacities and protocol message limits; they are not counted as pending-wire bytes. Memory backend transient chunk copies are store retention plus at most one replacement piece while holding its mutex; they are not disk PendingWire. Playback aggregation/resync and unrelated trusted chunk/read APIs retain their existing separate bounds and limitations. This is not a bound on total process RSS or arbitrary external callers retaining borrowed buffers.

Crucial unresolved implementation audit: verify live config validation really enforces finite W and legal P/C on every pool entry (fresh and tests/custom Continuity), and ensure no other cursor mutation bypasses the hold. If not, do not claim the bound: reject invalid internal configuration or bring the needed validation change back for approval. Do not silently add a cap/default. Reassembly generic add_block supports unusual offsets outside this live proof; do not generalize the proof to generic callers.

## Approval scope and risks

Approve only this explicit-ticket/retained-reassembly protocol and its intentional media hold: while unresolved publication exists, request/retransmit/cursor recovery pauses and accepted bounded incoming pieces accumulate in the fixed window. Event dispatch/cancellation continue. No new public configuration/default, detached publisher, unverified serving, early permit release, reciprocal-read redesign, activation/output redesign, live diagnosis, issue closure or release.

Largest risks: missing an indirect skip; allowing unrestricted take_ready after a later piece completes; failing to service retained Needed on reconnect; hidden mutex await after ack; starvation through prepolled peer events; metadata growth from duplicates; overclaiming fairness through unrelated blocking handlers. The stronger batch hold deliberately trades temporary freshness/request throughput for a small auditable memory proof. If that tradeoff is unacceptable, return for design revision rather than quietly implementing moving-window pinning or a worker queue. ## Root scope refinement

After inspection, root removed the proposed general rotating wake scheduler and unnecessary ready-prefix API. The chosen full-batch hold needs only a take_ready gate plus bounded completion lookup; publication polling is the only new fairness priority. This narrows the change and preserves existing unrelated wake policy. Existing live recovery validation rejects oversized reassembly horizons; implementation must verify every relevant fresh/custom entry uses it rather than claiming a generic reassembler bound. No production or test edits were made during design refinement.
